# Slice A: Bundle pipeline

Owner: Claude session, branch `slice/a-pipeline` · Phase: MVP · Migrations 0100–0199

## Goal
After upload, the expert gets a numbered, sorted bundle: every page read by OCR, its source and dates identified, facts extracted with links to the exact words, duplicates set aside, gaps and missing documents listed, and a ready-made email to ask the instructing party (the solicitor, under gb-eaw) for what's missing.

## Screens
- `S30-NotThisPatient` Not this patient's record (canvas board 30)
- 07 Preparing your bundle (`S07-Preparing`)
- 08 Your bundle is ready (`S08-BundleReady`)
- 08b Ask the instructing party for what's missing (`S08b-AskSolicitor`; pack label "Ask the solicitor")

## Endpoints (architecture 5.2)
- `POST /v1/cases/{id}/process` → 202 job; `GET /v1/cases/{id}/process` → the latest processing job (screen 07 follows it)
- `GET /v1/cases/{id}/bundle/summary`
- `GET /v1/cases/{id}/duplicates`; `PUT` and `PATCH /v1/cases/{id}/pages/{page_id}/duplicate`
- `PATCH /v1/cases/{id}/documents/{doc_id}` (provenance)
- `PATCH /v1/cases/{id}/missing-items/{item_id}`
- `POST /v1/cases/{id}/instructing-party-requests/draft`; `POST /v1/cases/{id}/instructing-party-requests` (returns `mailto:` link in MVP) The draft body takes `{extension: bool}` and returns `extension {days, due_date, after_date}` (pack `request_extension`), used by the S08b "Need more time?" aside.
- `POST /v1/cases/{id}/documents/append` → pipeline on new pages only
- `GET /v1/cases/{id}/pages/{page_no}/thumbnail` (for duplicate review)

## Tables owned
`ocr_words`, `missing_items`, `record_gaps`, `record_entries`, `instructing_party_requests`. Writes the OCR/source/duplicate columns of `pages` and inserts `facts` with status `suggested` (contract owned by foundation).

## Worker job: `process_bundle` / `process_pages`
split (pikepdf) → render 150–200 dpi (pypdfium2) → hashes → text-layer check (born-digital pages: words from pypdfium2, no OCR) → **T-07a** OCR (Azure DI Layout) for the rest → low-confidence flag → `pii.strip` → **T-07b** extraction (Sonnet 5, cached prompt), up to `extraction_batch_size` pages (default 10) per call, to stay inside the cell's Bedrock on-demand throughput ceiling — the model answers each page under its own `page_no`, never citing another page's word IDs → `provenance.check` per page → date normalisation (dateparser, date order from the pack) → duplicates (pHash + MinHash + rapidfuzz, with date/value equality) → record gaps (monthly density per source) → **T-07c** missing documents (references matched to inventory) → embeddings (bge-small) → email via Resend ("Your bundle is ready", no patient details).

## AI tasks (architecture 6.3)
| Task | Model | Output | Check |
|---|---|---|---|
| T-07a | Azure DI `prebuilt-layout` | words, polygons, confidence, handwriting | low confidence → screen 10 queue |
| T-07b | Claude Sonnet 5 (in-region) | one answer per page in `pages[]` (each carrying its own `page_no`): `source_type`, `printed_dates[]`, `facts[]`, `references_out[]`, `availability_evidence[]`, `actions_requested_of_clinician[]`, all with `word_ids` | value-in-span; any page's failure retries the whole batch once, then that page is `needs_human`; a page that passes but keeps little or nothing (`no_facts`/`low_coverage`) is asked once more on its own, keeping the second answer only if it keeps strictly more |
| T-07c | Sonnet 5 (candidate pages chosen by code, nearest by date then page number, until bge-small is in the cell) | `{reference_id, matched_page or null, confidence}` | unmatched, or a page the case lacks → missing list; expert confirms |

## Contracts
- **In:** foundation uploads, jobs, AI kit, `pages` and `facts` contracts.
- **Out:** `facts` (suggested, with `word_ids`, `bbox`, `event_date`, `availability_evidence`), page images and thumbnails, low-confidence queue (B), missing items (08b), appended-page processing (reused by G).

## Records transcript (ADR 0028)
- T-07b returns `entries[]` (kind, first and last word id, author role, specialty); stored in `record_entries` (0121, purge order 1015). Job `extract_entries` backfills pages read before this change. An entry that overlaps the one before it is trimmed to start after it (empty ones are dropped and counted). Entry dates: a birth date is never used, whether recorded or printed directly after a birth label (the pack's identifier recogniser says which text is a date of birth, so a case with no recorded date of birth is covered; the same date printed again elsewhere on the page is the birth date too); a recorded date of birth is matched on its printed day, month and the last two digits of the year; a two-digit year is read in the pack's date order, only by the repair job, in the latest century not after the whole bundle's latest full date and not before the date of birth when known (`printed_century`); extraction never reads it (the "latest so far" depends on page order), and when no century fits it still blocks the entry (`please_check`); then one distinct date is used, else the one on the entry's first printed line (not for the entry holding the page's first word, which holds the header), else `please_check`; a date taken only from the last printed line by an entry that reaches the page's end and has lines before it (a footer) is `please_check`. An entry holding three or more lines that start with different printed dates (a card with a line per visit; not the pack's letter kind; two dates are a result's sample and report dates) is split into one entry per dated line (`extract.split_at_dated_lines`: contiguous word ranges that cover the entry, no model call; two dated lines in a row with the same date stay together; a piece that would be only the page's first or last line stays with its neighbour), in extraction and in the repair job. The repair job (`repair_fact_dates`) dates entries that have none, dates again an entry whose date is a birth date, splits a dated card the same way, and takes the line directly above (`line_above`) only when the entry printed no date and the date lies in no entry of the page; an entry with a date of its own is otherwise never changed. A page with enough words whose entries cover under 80% of them is asked once more (`low_entry_coverage`). Duplicates: the picture hash is not asked when word similarity is at least 0.95, and separators between two digits (`/ . : - ` or a space; not a comma) do not make a changed number, in a date, a long identifier or a number whose groups all have two digits or more (`1/2` is not `1.2`, `10 5` is not `10.5`). Word similarity of 0.6 or more makes a likely pair (the word-by-word check stays strict); a header or footer one copy may lack is a run of 3 to 12 typed words with no digit that starts or ends at least three other pages of different content (`edge_runs` counts each distinct page once and leaves the page under test out); a line that is only moved is never a copy (its list or dated entry may be what it means). A page asked again for thin entries is counted by the cost guard like any call; when it trips the run pauses with nothing half-written. Every OCR call carries the pack locale. Slice B reads through `core/contracts/record_entries.py` (`entries_for_case`, `entries_ready`, `entries_status`, `request_entries`).
- Pages the model could not read: a batch answer that leaves pages out has just those pages asked again on their own (`asking.answer_group`), so one page costs only itself. One definition (`record_entries.retryable_unread_page_ids`) says which pages can be tried again: entries failed (whatever the label), words to read, not set aside, not copies. The job, `failed_pages` on the summary and the transcript button all use it. `POST /transcript/retry` (and the S08 button) tries the page retry first, else the entries job after it failed; it queues the worker job `retry_unread_pages` (0131, action `page.read`) once (advisory lock per case), which marks only those pages to be extracted again and rejects their unverified suggestions. Their failed marker stays until an extraction succeeds, so a retry that fails every attempt can be pressed again. Good pages and verified facts are never touched; nothing retries by itself. `GET /bundle/summary` carries `failed_pages` and `retrying` (pages failed and an entries or retry job waiting); S08 says "N pages weren't processed" with a "Try these pages again" button and polls while `retrying`. While a retry runs the transcript is `preparing` (not ready) with the words "trying the pages we couldn't read again"; its contents offers the button only to people with `page.read` and when `failed_pages > 0`.
- Retry progress: `GET /bundle/summary` also carries `retry` (`{running, paused, pause_reason, allowance_used_up, total, done, failed}`, or null), counted by the server (`repo.retry_progress`) from the latest `retry_unread_pages` job and the pages that run took (`page_analysis.retry_job_id`, set by `reset_unread`, migration 0132): done = entries read since the job was queued, failed = failed again since, total adds the pages still waiting. Pages the run did not take, copies, set-aside and word-less pages are never counted. `running` is true while the job is queued or running, or handed back (`resuming`) with a queue row still waiting for or held by a worker (`app.job_waits_in_queue`; a hold placed before the worker picked it up leaves `resuming` with no row, which is not running); `paused` while it is held back (e.g. the cost guard): S08 and the transcript's preparing screen then say "Trying again has paused for now. Please check back in a little while." and stop asking. A pause that is not resumable (the cost guard, the key service unreachable) never ends by itself, so it is not a dead end: `retry.pause_reason` (`cost_guard` or `other`, a fixed code, never text) picks the line ("This case has used up its processing allowance for now." or the general one), S08 and the transcript's preparing screen keep "Try these pages again" / "Try again" for people with `page.read` (but not while the case is still over its allowance: `retry.allowance_used_up`, computed from `app.ai_budget` and the cell's cost-guard settings, shows "This case has used up its processing allowance. Please contact support." (`bundle.retry_allowance_used_up`, `transcript.retry_allowance_used_up`) and no button), and a press hands the same paused job back to the queue (`record_entries.request_unread_retry` -> `app.resume_paused_job(job, queue)`, migration 0133: the queue must be `jobs`, the priority is the job's own and the queue row always takes a lock like 0035's; status stays `paused` with the short code `resuming` until the worker makes paused -> running; never a second job or queue row; refused while the case is on hold, and refused with 409 `allowance_used_up` while the case is over its allowance, `record_entries.case_over_allowance`; the screens show the same allowance line, also when a press meets that refusal). - Answers cut off at the output cap: raising the cap is the main fix (`ANTHROPIC_LIMITS.max_output_tokens` 32000, the direct client always streams; Bedrock fallback stays 16000; direct concurrency is 50 so concurrency x cap stays 1.6M of reserved output tokens). ## Worker connections and stuck jobs (production fixes)

- Pools: the worker's own pool (`WORKER_DB_POOL_MAX`, default 10) and the queue library's (`WORKER_QUEUE_POOL_MAX`, default 4) add up to less than a session pooler's pool size (15 by default; F51). Model calls in flight (`service._extract_concurrency`) are the provider's limit, at most the worker pool less `POOL_RESERVE` (2), at least one: by default only about 8 model calls run at once, on 10 + 4 pooler connections per worker replica. A second replica, or any other client on the same pooler role, needs more pooler capacity: raise the Supabase pool size first, then `WORKER_DB_POOL_MAX` / `WORKER_QUEUE_POOL_MAX` (`docs/runbooks/railway.md`).
- Dropped connection (F52): `JobWorker._persist` tries a job's status write again on a fresh connection (`DEFAULT_PERSIST_WAITS`); `JobWorker.requeue_orphaned()` (worker start and each housekeeping round; `app.requeue_orphaned_jobs`, migration 0134) puts back a `running` job whose queue row is no longer todo/doing, within `max_attempts`. The put-back writes name the status they move from, so a retry after a commit that went through is a no-op, and the sweep (migration 0135) also gives a `queued` job with no todo/doing row a new queue row, never one tagged `case_on_hold`.

## Page-batch jobs (scalability PR 17: design; build is a later PR)

Status: design for review (revised after the Opus review). ADR `docs/decisions/0038-page-batch-jobs.md`. Today one `process_bundle` job (kind `process_bundle` or `process_pages`) holds the lock `case:<id>` and one worker slot for the whole bundle (split, ocr, sort, duplicates, missing, embed, ready), so the expert's own `rerun_checks` and `build_report` wait for hours and one 4,000-page bundle holds a slot for 75 minutes or more. Goal: read the pages in about 100-page child jobs on the `bulk` queue that take no case lock, keep the cross-page steps under the lock, and leave the browser, the API and the SSE stream as they are.

### Switch and numbers (scalability rule 9: the default equals today)
- `PIPELINE_BATCH_PAGES` (default `0` = off, today's single job, unchanged; recommended `100` once PR 18 has measured). `PIPELINE_BATCH_WINDOW` (default **2**): child jobs of one run queued or running at once; it must be at most `WORKER_CONCURRENCY - 1` of the `bulk` worker (4 in `docs/runbooks/railway.md`, so 3), checked at worker start (a warning with the numbers only), so one bundle never takes every `bulk` slot: one stays free for the bundle's own tail, another bundle's children and the other bulk jobs. `PIPELINE_BATCH_MIN_PAGES` (default = `PIPELINE_BATCH_PAGES`): fewer pages to read (a 14-page append, a small bundle) stay in one job as today. Read through `app/core/config.py` (foundation adds them). A run already planned finishes the way it was planned, whatever the flag says later.
- Child kind `read_page_batch`, `interactive=False`, `changes_case=False` (no lock), `bulk` queue, priority 0. Registered in `features/pipeline/__init__.py`, listed in the `api/AGENTS.md` job table and architecture section 7 (foundation-owned: ask), mapped to action `case.upload` in `app.job_kind_actions`. It is not in `BUNDLE_JOBS`, so the routes never list it and `request_cancel` ignores it.

### Why the single job cannot just be cut up: what a page depends on
The review of `service.py` and `repo.py` found calls in the per-page steps that look across pages. Each is dealt with, or the pages could not be read in separate jobs and give the same answers:
| Call | Reaches | Answer |
|---|---|---|
| `_load_page` -> `repo.previous_page_words` | page N-1's words (another batch's) for the running header | Two phases (below): all words exist before any page is extracted, and words are final once written, so the header is the same as in one job |
| `_load_page` -> `latest_printed_date` | max printed date over pages extracted so far (it changes as pages finish) | **Frozen at plan time**: the parent computes it once when it plans the extraction batches, stores it in `pipeline_runs.date_anchor`, and passes it to `_load_page(anchor=...)`; flag off keeps today's rolling value |
| `_extract` -> `repo.reset_undone` | every page of the case brought back from quarantine | Run **once in the parent** at the start of the extraction plan; a child given a page range never calls it |
| `_read_words` -> `repo.pages_without_language` | every page of the case without a language | Run **once in the parent** after the OCR phase (step `name_language`); a child names nothing |
| `_read_words`, `_extract`, `_embed` -> `pages_without_words`, `pages_to_extract`, `pages_to_embed` | the case | Take optional `first`/`last` page numbers; a child passes its range |
So "same results as flag off" holds for words, entries, facts (for the same recorded model answers), page analysis, embeddings, duplicates, gaps and missing items, **except** the two-digit-year anchor, which is the plan-time maximum instead of a value that moves as pages finish (in one job with concurrent batches it already depended on timing). Step 6's equivalence test uses a bundle whose printed dates make both give the same, and a separate test pins the anchor to `latest_printed_date` at plan time. A test with a spy repository lists the repository functions a child may call (all page- or range-scoped); any call taking only the case id fails it.

### What takes the case lock and what does not
| Step | Runs in | Lock `case:<id>` | Why |
|---|---|---|---|
| split (pikepdf, render, numbering), plan OCR | parent, first run | yes | assigns `bundle_page_no`; two plans of one case must not overlap; takes over open runs (below) |
| ocr: `_read_words` over the batch's pages | child | no | writes only that page's `ocr_words` and `pages.text_source` |
| name_language, then plan sort (`reset_undone`, anchor, batches) | parent, second run | yes | whole-case reads and writes |
| sort: `_extract`, then `_embed`, over the batch's pages | child | no | writes only that page's analysis, entries, suggested facts, vector |
| wrong-person suggestion, duplicates (hash, compare, set aside), gaps and missing documents (T-07c), ready | parent, last run | yes | look across pages; ready changes `cases.status` |

While children run the parent holds nothing, so `rerun_checks`, `build_report`, `export_case` and every other case job go ahead. The lock is held for the split and two short planning runs, and for the tail. PR 18 measures the tail; a second wave (T-07c as batch jobs) is the follow-up if it is more than about 10 minutes at 4,000 pages. Children writing without the lock is safe because ranges are disjoint, nothing reads an unverified suggestion as fact (rules 2 and 3), and **every child write goes through the guard below** (the stores do not check anything today). Kinds that relied on the lock to wait for the bundle (`reprocess_case`, `retry_unread_pages`, `extract_entries`, `repair_fact_dates`) **wait without holding a queue row**. A paused job that the worker resumes by itself (`_ResumeLater`, F5) keeps a `todo` queue row with a future `scheduled_at` and its lock `case:<id>`; procrastinate's `procrastinate_fetch_job_v2` (`schema.sql`) refuses a locked job while any other `todo` row with the same lock has a higher priority, or the same priority and a lower id, whatever its `scheduled_at`. A sleeping waiter (priority 0, queued before the parent's wake) would therefore block the parent's wake and every new bundle job, and re-pause until it dead-lettered after 2 hours. So a waiter that finds an open run raises `ProcessingPaused("busy_processing")`, which is **not** in `RESUMABLE_PAUSES`: the worker ends its queue row and leaves the job `paused`. The test is one SQL function, `app.pipeline_case_busy(case, resumable)`, used by the waiter at its start and by the sweep: the case is **busy** when it has an open run (not `done`, not `closed`) and any of: (a) a child of the run has a **queue row** `todo` or `doing` (a child paused `service_busy` has a sleeping `todo` row and counts, whatever its job status says); (b) the parent is `running` or `queued`; (c) the parent is `paused` with a code in `RESUMABLE_PAUSES` (the worker will resume it by itself, and its children wake with no lock). The set is the foundation constant, passed in by the caller as an array (`app.pipeline_case_busy(case, resumable text[])`, and `app.pipeline_heal_runs(resumable text[])` for the sweep) and never copied into SQL, so it cannot drift. Queue-row state, not job status, decides about children: without (a) and (c), two children that both raised `service_busy` (`service.py:546`) and a parent mirrored to `paused service_busy` would count as idle, `reprocess_case` would be handed back, and it would run while the children wake and write the same pages. A run left open by a Stop (`cancelled`, children ended without queue rows), a cost-guard pause or a permanent failure is **not** busy, so a Stop does not strand the waiters until another `POST /process`. The sweep hands a waiter back (`status = 'paused'`, `error_code = 'busy_processing'`, no `todo`/`doing` queue row, case not busy) with `app.pipeline_redefer`, re-checking `pipeline_case_busy` under the run rows' `for update` locks. A later reopen cannot race a handed-back waiter: a reopen (Try again, `POST /process`) is run by a parent job, which holds `case:<id>`, the same lock the waiter holds while it runs, so they never overlap; the waiter's own first act is `pipeline_case_busy`, and if a reopen got in first it pauses `busy_processing` again. No timer, no back-off, no row in the lock's queue while it waits. A waiter keeps its **own** priority (the wake alone has the higher one), so handed-back waiters do not jump other cases' `bulk` work. The waiter's `error_code` stays `busy_processing` until the worker starts it (which clears it), so a hold that swallows its queue row leaves it findable: the sweep hands it back after `release_case_hold` (below). `repo.latest_processing` and the bundle summary ignore a job `paused` with `busy_processing` (it is waiting, not a failure), so S07 shows no paused panel in the 30 seconds between the run ending and the hand-back; a green step with a test.

### The write guard (children only)
Today `store_words`, `store_extraction`, `store_entries` and `store_embedding` in `repo.py` write whatever they are given; the lock and the job order were the only protection. In batch mode every child page write is one transaction that begins with `repo.batch_write_allowed(conn, batch_id, page_id)`: it takes `select ... from pipeline_runs where job_id = <run> for share` and then the page row, returns false (the child ends quietly, writing nothing) when the run is missing or `closed`, and returns false when the page is a confirmed or deleted quarantine, superseded or deleted. The guard takes the **page row `for share`** first (a plain read does not wait under read committed) and reads the quarantine status in a later statement, so it sees anything committed before it got the lock. Quarantine confirm (slice A, S30) locks the same page row `for update` before it changes the quarantine, and `for update` conflicts with `for share`: a confirm that is already running makes the child wait and then refuse; a child that got the lock first finishes its write before the confirm proceeds. Test with two connections. `for share` on the run row is also what lets a purge lock the children out (F64). The four stores themselves stay as they are; the guard is a repo function the child calls before them (a green step with a test for each store call site, below).

### Shape: one `jobs` row for the person, child jobs for the work, two phases
The parent stays the single `jobs` row `GET /process`, `/bundle/summary`, retry, cancel and screen 07 follow. Children are other `jobs` rows (`read_page_batch`) those routes never list. No job status is added.

1. **First run** (lock held): `ctx.step("split")`, then `ctx.step("plan_ocr")`: one transaction that first **takes over the runs that are not healthy** (paused, failed or stopped; healthy runs stay open, below), reads `pages_without_words` and `pages_to_extract`, drops pages in an open run's range, and decides on the **union** of the two (a page with words that is still to be extracted counts: after a stop during the sort of a 4,000-page bundle `pages_without_words` is nearly empty, and counting only OCR would read 4,000 pages inline under the lock for an hour). Fewer than `PIPELINE_BATCH_MIN_PAGES` in the union, or the flag off: no run, today's inline path. Otherwise it cuts the pages without words into batches of `PIPELINE_BATCH_PAGES` by `bundle_page_no`, inserts the `pipeline_runs` row (`state = ocr_waiting`) and the batches (`phase = ocr`) and queues the first `PIPELINE_BATCH_WINDOW` children with `app.enqueue_job` (new `jobs` rows). With no page to OCR the run starts at `ocr_ready` and the parent goes straight on to wake A's steps in the same run, and with no page to extract it goes straight to the tail; it parks only when it queued children. The handler then raises `JobParked` (new, foundation): the row stays `running`, no `_finish`, the queue row ends, the slot and the lock are free.
2. **OCR children** `read_page_batch(batch_id)`: `run_step`-style `_read_words(first, last)` then `ctx.step("ocr", _noop)`; then **a transaction of its own, after the page-write transactions have committed**, calls `app.pipeline_complete_batch` (a page write holds the run row `for share`, the fan-in takes it `for update`: in one transaction two last children would each hold the share lock and ask for the update lock and deadlock, `40P01`). Completion is idempotent, so a child that crashes before it retries, skips the finished pages and completes. The per-page checkpoint (`text_source is null`) is the progress; a retried child redoes only missing pages.
3. **Wake A** (`ocr_ready`, the parent's second run): `ctx.step("name_language")`, then `ctx.step("plan_sort")`: `reset_undone`, the date anchor, batches for `pages_to_extract` (`phase = sort`), `state = sort_waiting`, the first window of children; park again.
4. **Sort children**: `_extract(first, last, anchor)` then `ctx.step("sort", _noop)`, `_embed(first, last)` then `ctx.step("embed", _noop)`; complete as above.
5. **Wake B** (`sort_ready`): claim `finishing`; the tail steps `_suggest_quarantine`, `duplicates`, `missing`, `ready` (existing `_ready`), then **`run_done`** and the bar at 100.

Every step is a `ctx.step` checkpoint written **after** the work, as `process_bundle` does (`run_step`, then `ctx.step(step, _noop)`, `service.py:1289-1296`): `JobContext.step` (`jobs.py:261`) holds one checkout while its `work(conn)` runs, so it never wraps the page work, or it would break "no second checkout while holding one" (Bounds below). So a crash in any parent run retries that run and skips finished steps. **Handler entry** (batch mode) is one call, `app.pipeline_enter(run)`, under the run row lock, which first **sets its own `doing` queue row's priority back to the job's own `jobs.priority`** (the wake row carries `WAKE_PRIORITY` 20 so that it is fetched; a procrastinate retry keeps the row's priority, so without the reset a tail that pauses `service_busy` or `model_unavailable` (`_suggest_quarantine`, T-07c) would sleep as a `todo` row at 20 holding `case:<id>` and block `rerun_checks`, `build_report` and `export_case` at priority 10 for up to `MAX_WAIT_SECONDS`, 2 hours; today the bundle row sleeps at `BATCH_PRIORITY` 0 and blocks none; the row is found with `search_path = ''` as `procrastinate.procrastinate_jobs` where `args ->> 'job_id'` is the job and `status = 'doing'`, and the alternative, `RetryDecision(priority=...)` in `_RetryOnlyWhenAsked` (`jobs.py:287`), is not taken because it needs the job's own priority carried through `_ResumeLater`, a foundation change), then returns what to do and never queues a second row: `closed`/`done` -> end (a superseded parent finishes `done`, writing nothing); `ocr_waiting`/`sort_waiting` -> reopen the run (below), then if no batch of the phase is open set the phase `*_ready` here (no queue row: this run is the one) and continue, else park; `ocr_ready` -> wake A; `sort_ready` -> claim `finishing`, tail; `finishing` -> tail (resuming). A stale queue row for a job already `done` does nothing (worker change below), and the lock serialises two rows of one job.

**`run_done` is its own step, outside `_ready`'s guard.** `_ready` returns early when `repo.split_in_job` is false (a `POST /process` that split nothing new), so putting the end of the run inside it would leave the run `finishing` forever and block every younger run. `run_done` calls `app.pipeline_finish_run(run)`: `finishing -> done`, then `app.pipeline_fire_next(case)` for the case's next run, in its own transaction, whether or not `_ready` did anything.

### Taking over: cancel, a new `POST /process`, and runs that never close
A cancel pauses the children (`ProcessingPaused("cancelled")` at a page boundary), the sweep pauses the parent with `cancelled`, and today nothing resumes a cancelled job: the expert presses start and `POST /process` queues a **new** `process_bundle`. If the old run stayed open the new parent's fire would wait for it (plan order, below) and the case would deadlock. One model, no exceptions: a new plan **takes over only the runs that are not healthy** and leaves healthy ones alone.
- `ctx.step("plan_ocr")` begins with `app.pipeline_close_runs(case, by_job)`. For each open run of the case it first runs the sweep's mirror (below), so a pause or failure that the sweep has not yet written is seen, then **closes the run** (`closed`, `closed_at`, `closed_by_job_id`) when its parent is `paused` or `failed`, or a stop was asked after the parent was created (and after `reopened_at`), so a cancel and a start within one sweep round still take over. A run whose parent is `running` (or queued) with no stop asked is healthy and is **left open**.
- A closed run's parent, if it was still `running`, moves to `paused` (`cancelled`) so it does not look live or outrank the new parent; its queued children are started by the worker, find the run closed and end writing nothing (`queued -> running -> done`; `jobs_guard` has no `queued -> done`), a running child fails the write guard at its next page, paused or failed children are inert. A parent retried or resumed whose run is `closed` ends `done` at once.
- An append or a second `POST /process` while a healthy run is open therefore does not touch it: the new plan drops every page inside an open run's range and reads only the others, and the new run's fire waits for older runs (plan order, below). Pages the closed run had not finished are planned again by the new run through the per-page checkpoints, so nothing finished is read twice.
- **Stop after a reopen.** `cancel_requested` compares `case_processing.cancel_requested_at` with the job's `created_at`, and `repo.request_cancel` writes a new stop only when the stored one is older than the newest live bundle job's `created_at`. After a Try again the parent and its children would stop at once (the old stop is newer than `created_at`), and a second Stop would do nothing (the stored stop is newer than the parent's `created_at`). `pipeline_runs.reopened_at` fixes both with one rule: in `repo.cancel_requested` (the parent's own check in `_stop`, and the children's, which ask about the parent's id) and in `repo.request_cancel`'s "newest live job" the timestamp is `greatest(created_at, reopened_at)`, with `reopened_at` taken from the job's run when it has one. A stop before the reopen is ignored; a stop after it stops the children again and `request_cancel` returns true.

### Fan-in: exactly once, crash-safe
`app.pipeline_complete_batch(p_batch)` (SECURITY DEFINER, worker role, refuses unless `app.current_job_case_id()` equals the batch's case) runs in the child's last transaction:
1. `select ... from pipeline_runs where job_id = <run> for update`: the lock that makes the last two children safe (under read committed each would otherwise see the other's batch open and neither would fire).
2. `update pipeline_batches set completed_at = coalesce(completed_at, now())`.
3. Top up the window: while fewer than `PIPELINE_BATCH_WINDOW` children of the run are queued or running and a batch of the current phase has no child, queue one with `app.enqueue_job`. This is what keeps one 40-batch bundle from queueing in front of everything else: each completion queues one behind whatever is already waiting on `bulk`.
4. If no batch of the current phase is open, the state is that phase's `*_waiting`, the parent `jobs` row is `running`, and no *older* run of the case is `*_waiting`/`*_ready`/`finishing` **with a `running` parent** (an older run whose parent is paused or failed does not hold back a younger one; its own tail recomputes the whole case when it later runs): `update ... set state = '*_ready' where state = '*_waiting'` and, only if a row changed, call `app.pipeline_redefer(parent)`: a new queue row for the **existing** parent job (never `app.enqueue_job`, which inserts a new `jobs` row, i.e. a second parent), built as `app.resume_paused_job` (9001) builds one, with the queue and lock of its latest queue row (`case:<id>`), **priority `WAKE_PRIORITY` (20)**, and `requeued_stall = true` on the parent (below). One transaction: both or neither; a second caller finds the state already moved. The priority matters: a wake row has the case lock, and a sleeping back-off row of another job of the case (a build paused `service_busy`, F5) with the same or a higher priority and a lower id would otherwise keep it from ever being fetched; above the interactive priority (10) nothing can block it but a job running now.
Runs of one case with running parents finish in plan order (a younger run's tail should see an older run's pages, or a reference to a page still being read would be listed missing for a while); `app.pipeline_finish_run` fires the next run.

**A wake is not an attempt.** `_run_job` adds 1 to `attempts` unless the job was paused or `requeued_stall`; `requeue_orphaned_jobs` compares `attempts` with the maximum. Each wake (two per run, plus a tail retry) would use up the three attempts of a healthy job. `app.pipeline_redefer` sets `requeued_stall = true` on the parent for a wake. The column and the rule already exist on main (migration 0058 added `app.jobs.requeued_stall`, `jobs.py:479-480` runs `update app.jobs set status = 'running', error_code = null, requeued_stall = false, attempts = attempts + case when status = 'paused' or requeued_stall then 0 else 1 end`). That update does not care what the status was: for a parent that is already `running` the `running -> running` write is no transition (`jobs_guard` only checks a change), so a wake counts nothing and **no `jobs.py` change is needed**; the stall sweep (`requeue_stalled`, `jobs.py:410`) sets the same flag. The design relies on it, so a test pins it (step 5): start (`attempts = 1`), wake A, wake B leave `attempts = 1`, and a tail error afterwards is retried (attempts 1 of 3), then fails the job only after the maximum. The orphan sweep compares the same counter.

### `app.pipeline_redefer` and the lock order
`app.pipeline_redefer(p_job uuid, p_wake boolean default false) returns boolean` (0137; `security definer`, `set search_path = procrastinate, pg_catalog` like 0022 and 9001 so `procrastinate_defer_jobs_v1` resolves, every other object schema-qualified; `revoke execute ... from public, app_api, app_worker`, `grant execute ... to app_worker`; it checks no person, its callers are `pipeline_complete_batch` (which has checked the case), the sweep and `pipeline_finish_run`). It locks the `jobs` row `for update` and **returns false, changing nothing,** when: the job or its case is gone or the case is `deleted`; the case is `on_hold` (read without taking the `cases` row lock: the pickup check `job_waits_for_hold` is the authority, and a run row is never held together with a `cases` lock); the job is neither a `running` parent (wake) nor a `paused` waiter; or it already has a `todo`/`doing` queue row (idempotent). Otherwise it defers one row for the **existing** job: the queue and lock of its latest queue row (fallback `bulk` and `case:<id>`), priority `WAKE_PRIORITY` (20) for a wake and the job's own `priority` for a waiter, and for a wake it sets `requeued_stall = true`; it never changes `status` or `error_code` (the worker's start does). A refusal for a held case is not lost: a wake refused leaves the run in `*_ready`, which the heal sweep re-wakes after the release (F69); a waiter refused stays `paused` `busy_processing`, which the sweep hands back after the release. `app.job_waits_for_hold` returns true for any status but tags only a `queued` job, so a paused waiter or a `running` parent whose pickup meets a hold simply loses its queue row, and the same two sweep rules recover it; they never loop, because the sweep does nothing for a held case. `pipeline_redefer` handles only a `running` parent or a `paused` waiter, so `pipeline_reopen_run` (failed and paused children) cannot call it: both build their queue row with one internal helper, `app.pipeline_defer_row(job, queue, lock, priority)` (`set search_path = procrastinate, pg_catalog`, no grant to any role; it is called only from definer functions, which run as the owner), so the `procrastinate_defer_jobs_v1` call resolves in both (with `search_path = ''` it cannot find `procrastinate_jobs`).

**One lock order, everywhere** (so no two functions deadlock): the case lock `case:<id>` (procrastinate, held by parent runs and waiters) -> `pipeline_runs` row -> page rows -> `pipeline_batches` rows -> `jobs` rows -> queue rows. No function takes a `cases` row lock while it holds a run row. `pipeline_complete_batch`, `pipeline_reopen_run`, `pipeline_close_runs`, `pipeline_finish_run`, `pipeline_heal_runs` and `pipeline_enter` take the run row `for update` first, then batch and job rows. The child write guard takes the run row `for share`, then the page row `for share`. `purge_case_rows` deletes tables in `case_purge_order()` order, which would take batch rows before run rows; so 0136 adds a `before delete` **statement** trigger on `pipeline_batches` that, when `app.purging_case_id` (set by `purge_case_rows`) is set, locks that case's `pipeline_runs` rows `for update` first. Test: `delete_case` run concurrently with the last child's completion (two connections, barrier) ends with no `40P01` and no row, and a completion that finds its run gone returns quietly.

### Heal sweep, mirroring, pause, failure, resume
Foundation adds `JobRegistry.sweep(name)`; sweeps registered by features run in `JobWorker._housekeeping` beside `requeue_stalled` and `requeue_orphaned` (a failing sweep logs only the exception type). The pipeline registers `app.pipeline_heal_runs()`.

**Context.** The sweep runs on `database.anonymous()`: no person and no `app.job_case_id`. `app.enqueue_job` (0015) raises `42501` unless `app.current_job_case_id()` equals the case or the person has access. So `pipeline_heal_runs` is SECURITY DEFINER (`set search_path = ''`, objects schema-qualified, execute granted to `app_worker` only) and, for each run it works on, calls `perform set_config('app.job_case_id', <case>::text, true)` before the enqueue and `set_config('app.job_case_id', '', true)` after. Top-ups of **children** use the normal `app.enqueue_job` (they are new `jobs` rows), so the action and case checks stay in one place; the setting is transaction-local. Waking the **parent** never uses `app.enqueue_job` (that would insert a second parent): it is `app.pipeline_redefer`, a queue row for the existing job. Test: the sweep run as the anonymous worker connection tops up and fires, and the number of `jobs` rows of kind `process_bundle` stays one.

For each open run (rows `for update skip locked`; a run being reopened or completed is skipped this round):
- heal a lost fire or top-up (steps 3 and 4 above), and **re-wake a stranded parent**: a run in `*_ready` or `finishing` whose parent is `running` with no todo/doing queue row, while the case is not on hold, gets `app.pipeline_redefer`. This covers a hold that arrives while the wake row is being picked up (`app.job_waits_for_hold` tags `case_on_hold` only a job with status `queued`, so for the `running` parent it does nothing but make the worker end the queue row, and `app.release_case_hold` re-defers only `queued` jobs tagged `case_on_hold`); the parent would otherwise sit `running` for ever. While the case is on hold the sweep does nothing for it, so no wake loops; the first sweep after the release wakes it. A **queued** child held by `case_on_hold` is handled by hold and release as today (`release_case_hold` keeps the earlier row's lock, null for a child). A job that is `paused` with a resumable code is **not**: it keeps a sleeping `todo` row, and if a hold is placed and the worker then picks the row up, `job_waits_for_hold` tags only `queued` jobs, so the row ends and the job stays paused with no row (`release_case_hold` re-queues only `queued` jobs tagged `case_on_hold`; F5's Try again appears only after a failure, which can no longer happen). So the sweep also re-defers, when the case is not held, with `app.pipeline_defer_row` (its `error_code` is left as it is and the worker's start makes the paused -> running move without an attempt): (i) **a child** of an open run that is `paused` with a code in `resumable` and has no `todo`/`doing` row, with no lock and the queue and priority of its previous row; (ii) **the parent, only when its run is in `*_ready` or `finishing`** (it paused in its own handler, e.g. the tail, so nothing else will wake it) **and no child of the run is paused with a resumable code or has a `todo`/`doing` row**, with `case:<id>` and its own `jobs.priority`. A parent mirrored `paused` while children of its run are still open is **never** re-deferred by this rule: it stays rowless until the children clear and the mirror's "no child paused or failed -> parent running" path wakes it. Otherwise the two rules would undo each other: child A pauses `service_busy` on a back-off, the mirror pauses the parent, the next sweep re-defers the parent, which reopens the run (`pipeline_reopen_run` brings A's sleeping row forward) and parks, A is throttled again, and the F5 back-off would be defeated every 30 seconds for up to 2 hours with the case lock taken each time. Without (i) and (ii) busy rule (c) would stay true for ever, the bundle would never finish and every `busy_processing` waiter would be stranded. **Pass order, fixed in `pipeline_heal_runs`, for each run under its row lock:** mirror first, then (i), then (ii) evaluated on the state the mirror left, then the stranded-parent wake (it comes after the mirror, so it sees the state the mirror left), then the top-up and the fire; a test pins it so no two rules can undo each other for one job. Every re-defer in (i), (ii) and the waiter hand-back takes the `jobs` row `for update` and **re-checks for a `todo`/`doing` row before calling `pipeline_defer_row`** (which has no row check of its own), so a heal racing `resume_paused_job` leaves exactly one row.
- **hand back waiters**: paused jobs of the case with `error_code = 'busy_processing'` and no `todo`/`doing` row, when `app.pipeline_case_busy(case, resumable)` is false (an open run left by a Stop, a cost-guard pause or a failure does not count; children with sleeping rows and a parent paused with a resumable code do) and the case is not on hold (`app.pipeline_redefer`, as above), rechecked under the run rows' lock;
- **mirror the children onto the parent**, only when the parent has **no todo/doing queue row** (a parent whose handler is running is not touched), and only for a child whose state changed after `run.reopened_at` (null counts as the start). A child `failed` -> the parent goes to `failed` with the child's code, and `jobs_guard` allows only `running -> failed` (not `paused -> failed`), so a parent that is `paused` (say child A paused `service_busy`, then child B failed for good) is moved `paused -> running -> failed` as two updates in **one transaction**; a parent already `failed` is left (Try again, `POST /process/retry`, `requeue_failed`, then re-enters `pipeline_enter`). A failed child always wins over a resumable pause. A child `paused` with a code other than `resuming` -> parent running -> paused with that code. When no child is paused or failed and the parent's pause code was resumable (F5), the parent goes paused -> running with no attempt counted. `resuming` (a stopping worker, F6) never touches the parent. All are transitions `state-machines.md` already allows;
- **keep the parent alive for the screen**: touch `updated_at` of a parked parent whose last update is older than 5 minutes, so `latest_processing` and `has_live_bundle_job` (a `running` row untouched for `LIVE_MINUTES`=30 is an orphan) keep treating it as live while its children wait in a backed-up `bulk` queue (the alert is at 900 s). With two parents on a case (an old closed one and the new one) the screen follows the newest `running` live one, else the newest; the closed parent is `paused`, so it cannot outrank. Routes tests cover a case with two parents.

**The resume race.** `_run_job` commits `running` for the retried or resumed parent before the handler's `pipeline_reopen_run` commits. A sweep in that gap would see the old paused or failed child and put the parent back. Three guards: the parent still has its `doing` queue row in that gap (the mirror skips it); `pipeline_reopen_run` sets `reopened_at = now()` and requeues the failed and paused children in one transaction under the run row lock the sweep also takes; and only children changed after `reopened_at` count. Test: a sweep between the two commits changes nothing, and the next sweep after the reopen sees running children.

`app.pipeline_reopen_run(run)` (SECURITY DEFINER, worker role, idempotent; it adds queue rows through `app.pipeline_defer_row`): failed children -> `queued` with attempts 0 and a new queue row with **no lock**; paused children -> queue row brought forward or deferred, no lock; batches without a child get one up to the window; running or queued children untouched; never a second child for one batch (`child_job_id` is set once).

**Null lock on every re-defer path.** A requeued or resumed child must not take `case:<id>`, or one child would block the case. Three SQL functions put a job back with `coalesce(v_lock, 'case:' || case_id)` or `case when seen then v_lock else 'case:'...`: `app.requeue_orphaned_jobs` (0134/0135, pipeline range: replaced in 0138), and `app.resume_paused_job` (9001, which replaced 0133/0064) and `app.support_job_action` (0035), both foundation. Rule applied to all three: a job that is a child of a batch (a `pipeline_batches` row has it as `child_job_id`) is re-queued with a null lock; otherwise the existing behaviour. The two foundation functions are replaced in **foundation 9002** (after 9001, which would otherwise overwrite a change made in a lower number). 9002 starts from the **current** definitions, not the first ones: `resume_paused_job` from 9001 and `support_job_action` from **0064** (which found the waiting row by job id on any queue; starting from 0035 would bring back the double run that 0064 fixed). A repository test in 9002's file keeps both behaviours: the back-off row on `bulk` is found by job id and no second row is deferred, and a batch child is re-queued with a null lock. The orphan sweep also skips a parent whose run is open and has no queue row (parked), and reads the latest queue row's lock whatever it is.

### Progress and SSE unchanged
Children report to the parent's row through `app.pipeline_report_progress(run)` (SECURITY DEFINER, worker role, checks `current_job_case_id`; pipeline-owned, so no foundation change to `JobContext.progress`). **One SQL statement** computes step, pct, `step_done` and `step_total` from live counts of the run's pages that are not quarantined or deleted (pages with words, pages extracted; so a page quarantined after the plan cannot leave the bar short of 100), and updates the parent with:

- the step is written only when its rank (`split < ocr < sort < duplicates < missing`) is at least the current one, and `step_done`/`step_total` are written with the step, so two children finishing at once cannot flip the label back or clear the counts;
- a tick every 25 pages per child.
The `jobs` NOTIFY trigger (0062) pushes the parent's change to open streams; the Preparing screen's step list is unchanged. Counts and step codes only (rule 6).

### Bounds on concurrency (the merged limiters stay the authority)
Every Azure OCR call takes the account-wide slot (PR 4) and every model call the model slot (PR 3), inside the child as in the parent today, so N children cannot exceed the provider ceilings; more children only wait. Per process: the `bulk` worker runs `WORKER_CONCURRENCY` (4) jobs on a pool of `WORKER_DB_POOL_MAX` (10) with `POOL_RESERVE` 2, so 8 connections are usable, and the pool itself has no acquire limit. Two things multiply connections, so one cap is not enough:
- **Nested `bounded()` calls**: `_extract` runs `bounded(batch, load)` inside `bounded(batches, one_batch)` (`service.py:786` and `:967`), so a cap on each call gives 2 x 2.
- **Connections that bypass `ctx.transaction()`**: `_ocr_slot` passes `ctx.database` to `kit.slot` (`service.py:1243`) and `kit.run_detached` / `_ask_detached` open `database.job(case_id)` directly (`core/ai/kit.py:273, 315, 632, 658`) for the cost guard, slot wait and release, and logging. A page in flight holds an account-wide slot while it needs a connection to release it, so a limiter on `ctx.transaction()` alone bounds some transactions, not the pages in flight.

So the rule has two parts, both with `cap = max(1, (pool - POOL_RESERVE) // WORKER_CONCURRENCY)` (2 today):
1. **A hard bound on pool checkouts per job**: a batch-mode handler calls `ctx.limit_checkouts(cap)` (new, foundation), which sets a per-job limiter in a context variable that `Database.job()` consults; `_run_job` runs the handler through a small wrapper whose `try/finally` resets the variable and sits **inside the `try` whose `except` branches call `_finish`**, so the reset happens before they run (a capped handler raising `ProcessingPaused` still writes its status when the pool is at the cap: tested) and the worker's own checkouts (`jobs.py:403, 448, 471`: sweeps and status writes) are never capped. Every checkout by that job's tasks (its own transactions, `ctx.progress`, `logged_step`, the kit's detached ones) takes one of `cap` permits for the time it is held. Nothing holds a checkout across slow I/O (PR 9) and no task opens a second checkout while holding one (a spy test fails on that, covering `ctx.transaction()`, `ctx.progress`, `logged_step` and the kit), so the limiter cannot deadlock: a page that holds an AI slot and needs a connection to release it waits only for another page's short checkout.
2. **Every `bounded()` concurrency in batch mode is at most `cap`** (`ocr_concurrency`, `_extract_concurrency`, `DB_CONCURRENCY` page work, `_embed`, and the tail's `duplicates` and `missing`), so pages in flight stay modest at each level and fewer tasks queue on the limiter.

Arithmetic: the window is at most `WORKER_CONCURRENCY - 1` (default 2). One bundle holds at most `window x cap + tail` = 2 x 2 + 2 = 6 <= 8 checkouts, and any 4 batch-kind jobs hold at most 4 x 2 = 8 = usable. Other `bulk` kinds are not capped and keep today's behaviour (a short acquire wait is possible, as now); the claim is that batch-kind jobs never hold more than their share, not that no acquire ever waits. The price: a child has up to 2 OCR pages and 2 model calls in flight (the nested levels are bounded by `cap` each and by the 2 checkouts below them), so one bundle alone has about 2 x 2 = 4 OCR pages in flight against about 8 in one job today. A lone bundle is slower per page unless the pool grows; the account-wide OCR limiter is the real ceiling, and PR 18 measures the 4,000-page time against the 75-minute target and tunes `WORKER_DB_POOL_MAX`, `WORKER_CONCURRENCY` and the window together. `docs/runbooks/railway.md` (the pool paragraph) gains these numbers in the same PR: a bigger `WORKER_CONCURRENCY` on the bulk worker needs a bigger `WORKER_DB_POOL_MAX` first, within the pooler's pool size. PR 2's metrics show the bulk queue's oldest age.

### Case deletion and holds while children run
`delete_case` waited on `case:<id>` behind the bundle job; children hold no lock, so a delete could start mid-run, destroy the key and purge rows while a child writes (a late write after the purge, a wrong certificate count). Slice H is not changed; slice A closes it from its side:
- The child write guard takes the run row `for share` in the transaction of every page write. `app.case_purge_order()` is children first (0017): the splice (migration 1024) puts `pipeline_batches` and then `pipeline_runs` at the **front**, so each table is emptied before the one it references and the certificate counts stay exact (`on delete cascade` on the foreign keys is only a safety net, never the way rows go). The purge locks the case's `pipeline_runs` rows `for update` before it deletes batches (a `before delete` statement trigger on `pipeline_batches`, 0136, keyed on `app.purging_case_id`), so it follows the global lock order above and cannot deadlock with a completing child; it waits for any in-flight child write transaction, then removes the rows; a child transaction that starts after finds no run and stops writing. `api/app/core/contracts/case_tables.py` (`CASE_TABLES`, and `PURGE_ORDER` with the same two tables first) must list both tables in the same PR, or the guard that compares the SQL order with the tuple fails.
- Files and key may already be gone when a child reads: it ends with an ordinary job error, retries, and finds the run gone (it stops, writing nothing); the failed tries use its attempts, which is harmless for a job about to be removed. A child's account-wide AI slot is freed by the slot context's own exit (`kit._release_slot_detached`, `kit.py:307`) as for any failing page today, by slot id; a build-time test checks that `delete_case` during children leaves no slot held, and if the release needs rows the purge already removed, the slot's expiry is the fallback and the finding goes back to foundation.
- A legal hold or `case_on_hold` already keeps queue rows from starting (`case_on_hold` tag); children and the tail stay queued and resume with the case. Running children finish their page.
Test: delete during children ends with no `ocr_words`, `facts` or `page_embeddings` row of the case, no child row written after the purge, and a certificate whose counts match what was removed.

### Build-time checks (each becomes a failing test the builder writes first)
1. **Pass order names the stranded-parent wake.** The pinned heal pass order is: mirror, (i) child re-defer, (ii) parent re-defer, stranded-parent wake, top-up, fire. The stranded-running-parent wake comes after the mirror; one test pins the whole order.
2. **The mirror skips a `failed` parent.** The mirror's "child paused -> parent running -> paused" path must not touch a parent already `failed` (`jobs_guard` rejects `failed -> running`). Test: child B fails for good, then child C pauses `service_busy`: the parent stays `failed` and the sweep does not raise.
3. **Mirror flips are cheap.** A mirror status flip does not count an attempt, takes no queue row and no case lock, and `updated_at` / SSE churn stays bounded (a sweep that changes nothing writes nothing; a flip is at most one event per change). Test: N sweeps over an unchanged run leave `attempts` and `updated_at` as they were.
4. **The mirror's wake of a rowless parent re-checks under the row lock.** The mirror's `paused -> running` wake of a parent with no queue row takes the parent's `jobs` row `for update` and re-checks there is no `todo`/`doing` row before it defers, the same rule as every other re-defer. Barrier test: the mirror's wake racing `resume_paused_job` on the parent leaves exactly one queue row.
5. **F69 end to end.** The last child completes while the parent is mirrored `paused`: the run stays `*_waiting` (fan-in does not fire into a paused parent); the next sweep fires exactly once (one parent queue row, one `*_ready` update).
