# 0038 Page-batch jobs: read a bundle in child jobs that take no case lock

Date: 2026-11-05 · Status: proposed (design; build is scalability PR 17) · Decided by: pipeline-owner, for the founder's review · Builds on: ADR 0037 (capacity plan), ADR 0021 (Railway, no data at rest), ADR 0013 (restricted roles) · See `docs/slices/A-pipeline.md` "Page-batch jobs" and `docs/ops/scalability-plan.md` PR 17

**Problem.** One `process_bundle` job reads a whole bundle (1,000 to 4,000 pages) while holding the lock `case:<id>` and one worker slot. Two effects: the expert's own `rerun_checks`, `build_report` and `export_case` wait behind it for up to 75 minutes (they take the same lock), and a single bundle holds a slot for that long, so 50 bundles at once need 50 slots of long jobs and one crash redoes the step queue from the last whole-step checkpoint.

**Decision.** Split the work that is per page from the work that is across pages.
- Per page runs in child jobs of about 100 pages (kind `read_page_batch`, `bulk` queue, no case lock), at most `PIPELINE_BATCH_WINDOW` (default 2, at most the bulk worker's concurrency less one) of one run queued or running at once. It runs in **two phases**, because pages look at their neighbours: all OCR batches finish first (the running-header read of page N-1 then sees final words), then the parent does the whole-case steps (language naming, `reset_undone`, the date anchor frozen at plan time), then the extraction-and-embedding batches run.
- Across pages (wrong-person suggestion, duplicates, gaps and missing documents, ready) stays in the parent job, under the case lock, run once after every batch is finished, ending in its own `run_done` step.
- The parent is still the only job the person sees. It plans the batches, **parks** (stays `running`, no queue row, no slot, no lock), and is woken by the last child of a phase through `app.pipeline_complete_batch`, which moves `pipeline_runs.state` from `*_waiting` to `*_ready` under a row lock and defers the parent's queue row (marked not-an-attempt) in the same transaction. That makes the fire exactly-once and crash-safe; a 30-second sweep (`app.pipeline_heal_runs`, with a transaction-local `app.job_case_id` so it can enqueue) repairs a lost fire.
- A newer bundle job takes over only the runs that are paused, failed or stopped (`closed`), so cancel then start cannot deadlock and an append does not kill a healthy run; every child write passes a guard that holds the run row `for share`, and the purge locks the case's run rows first (a statement trigger) then deletes batches, then runs, so deleting a case cannot race a child or deadlock with a completion. One lock order is documented: case lock, run row, page rows, batch rows, job rows, queue rows.
- Progress is written to the parent's row from live database counts by one SQL function (monotone step and pct), so the stream, the screens and the API are unchanged. The flag `PIPELINE_BATCH_PAGES` defaults to 0 (today's single job).

**Alternatives rejected.**
- *A new job status `waiting`.* It would reach the OpenAPI client, every screen's status mapping, the `app.jobs` guards and the support actions. A parked `running` row needs none of that.
- *The parent waits inside its slot, holding the lock.* Simplest, but it keeps both problems (slot and lock for 75 minutes) and removes the point.
- *A separate "finish" job row.* A second user-visible row to hide from retry, cancel, summary and SSE, and a second thing to keep in step with the parent's pause and failure.
- *Hooks in the worker to mirror a child's pause or failure onto the parent.* Faster than a 30-second sweep but spreads pipeline logic into `app/core/jobs.py`. The sweep keeps the foundation change to small hooks (`JobParked`, skip a stale row for a done job, `JobRegistry.sweep`, one migration for the null-lock rule). Latency of up to 30 seconds on a pause or failure notice is acceptable for jobs that take an hour.
- *Batching everything including duplicates and T-07c.* Larger win, but both look across pages and need a merge step. Measure the tail in PR 18 first.

**Consequences.**
- The shared Azure OCR slot (PR 4) and the model slot (PR 3) remain the bound on provider calls; more children only wait. Every job of the batch kinds, children and the parent's tail, holds at most `(pool - reserve) // concurrency` (2) pool checkouts in total, whatever the nesting of its `bounded()` calls and whoever opens the connection (a per-job limiter on `Database.job()` through a context variable, because the AI kit opens its own), and every `bounded()` concurrency is capped the same, and the default window is 2 (at most `WORKER_CONCURRENCY - 1`), so the pool is never over-committed and one bundle never takes every `bulk` slot.
- Pages are written without the case lock. This is safe because ranges are disjoint, nothing reads unverified suggestions as fact (rules 2 and 3), and a new repo guard (`batch_write_allowed`, called before each store; the stores themselves check nothing today) refuses writes for a closed run or a quarantined page. Tests cover it.
- Re-queue paths (`requeue_orphaned_jobs`, `resume_paused_job`, `support_job_action`) must give a batch child a null lock; foundation migration 9002 (after 9001, starting from 9001's `resume_paused_job` and 0064's `support_job_action`) and pipeline 0138 do it.
- The "same results as one job" claim has one stated exception: the two-digit-year anchor is the plan-time maximum, not a value that moves as pages finish.
- Kinds that used the lock to wait for the bundle (`reprocess_case`, `retry_unread_pages`, `extract_entries`, `repair_fact_dates`) pause with the non-resumable code `busy_processing` while a run is open and keep no queue row (a sleeping locked row would block the parent's wake, since procrastinate refuses a locked job while a same-lock `todo` row with higher priority or lower id exists); the sweep hands them back when the case is no longer busy (not busy: no child with a queue row, no running parent, no parent paused with a resumable code; a run left open by a Stop does not strand them). The wake's priority is reset to the job's own when the parent starts, so a tail that sleeps on a back-off blocks no interactive job, once, and not for a held case.
- Runs of one case with running parents finish in plan order so a later tail does not judge a page that an earlier run is still reading. A new plan closes only runs that are paused, failed or stopped; a healthy run stays open, so an append does not kill a running bundle.
- The parent's wake is a new queue row for the existing job (never `app.enqueue_job`, which makes a second parent), and the sweep re-wakes a parent whose wake a legal hold swallowed.
- New tables `pipeline_runs`, `pipeline_batches` (numbers, ids and one date only, rule 6); next free migrations 0136 to 0138, purge-order splice 1024 (batches then runs first; `PURGE_ORDER` and `CASE_TABLES` updated with it) and foundation 9002.
- Rules 1, 2, 5, 6, 7 and 11 hold unchanged because the children call the same read, extract and embed code.
- Rollback is the flag: set `PIPELINE_BATCH_PAGES=0`; a run already planned still finishes the way it was planned.
